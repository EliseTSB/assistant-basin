## Findings, most severe first

1. **HIGH — the primary oracle does not enforce token-exact replay, and neither gate validates the registered stop tokens. A wrong stop rule passes both checking algorithms.** Amendment 2 requires token-for-token agreement and fixes the two studies' stop rules (`PART87-DESIGN.md:109-117`). `replay87.regenerate` discards generated token IDs and returns `decode(..., skip_special_tokens=True).strip()` (`part87/replay87.py:259-260`); the final comparison checks that string alone (`:462-471`). The observer already supplies the necessary independent `token_ids_sha256`, token count and generated-step count (`observe.py:419-435`), but replay never compares them. Audit checks the saved text and token count against that run's own observer (`part87/audit87.py:317-322`), not against regenerated tokens. It also explicitly exempts `eos_token_id` and `pad_token_id` from the default comparison (`:77,347-354`) and never checks their registered values (`:361-379`).

   **Concrete control and mutant:** J13 changes only Part 87's 87B stop rule from `tok.eos_token_id` to `[tok.eos_token_id, tok.pad_token_id]` at `part87/part87.py:558`. On a tiny real Qwen2 bf16 model, the controlled fixture emits pad then eos for 87B. The correct run has token IDs `[0,2]`; the mutant stops after `[0]`. Both decode to the same empty answer. The unmodified replay checks **all 44 pilot rows**, reports zero problems/mismatches and exits 0; the unmodified audit, using its explicitly marked CPU fixture allowances, also exits 0. The observer's U row has token count **2 versus 1**, with different token hashes, and the calls record stop settings **2 versus [2,0]**. See `edge-token-results.json`, `edges-v3/token-control/`, `edges-v3/J13-extra-B-stop/`, and `probe_edges.py:12-54`. No replay checks were replaced; only its model loader supplies the tiny model. The tiny model's logits are controlled, while its forward, hooks, sampling and stopping code execute.

   This is a boundary counterexample, not a claim that production Qwen emits this sequence. It uses a real distinction in the pinned tokenizer: eos is `<|im_end|>` ID 248046 and pad is `<|endoftext|>` ID 248044 (locally cached `tokenizer_config.json:287,290`; extracted in `cached-tokenizer-facts.json`). The earlier im_end/eos fixture in `edges-v2` is superseded for this finding, because those two tokens coincide in the production tokenizer.

   **Fix:** return regenerated raw token IDs, hash them using the observer's exact encoding, and compare the claimed observer row's token hash and count. Independently enforce each study's effective eos set and pad token. Keep a regression in which visible text agrees while raw tokens differ.

3. **MEDIUM — audit can reject a correct bf16 intervention because it requires every operated position to change numerically.** `part87/audit87.py:180-191` requires changed layers/phases before considering whether a rounded operation had any visible effect; `:195-197` requires `changed_positions` to equal every eligible position. A valid subtraction of a small measured mean can round back to the original bf16 activation at some positions. This is especially relevant to M and random M; an exactly zero mean makes the valid M push zero everywhere.

   **Measured:** the initial unmodified tiny bf16 fixture's real measured means/doses and all 44 answers pass replay with no mismatches or problems, but audit rejects eight M cases with messages including `L6 changed in ['decode'], registered ['prefill', 'decode']` and `L6 prefill changed 1 of 3 positions`. See `probes/baseline/replay.json` and `probes/baseline/audit.log`. No wrong intervention was installed. For the mutation study I added fixture MLP biases to keep means away from zero; that revised unmodified control passes both checks (`probe_mutations.py:96-100`, `probes-v2/baseline/`). This is not evidence that the production means cause the failure, but it is a real false rejection of registered arithmetic.

   A second valid edge exists for D47: if the first generated token stops the call, decode mode correctly installs no numerical change at all. Audit still requires L22 in the changed-layer map before its `steps < 2` handling (`part87/audit87.py:179-189`). The first token control exposed four such false failures (`edges/token-control/audit.log`).

   **Fix:** distinguish hook execution/eligible positions from positions whose rounded value differs; verify bf16 arithmetic where observable. Allow the legitimate no-decode D47 case. Do not fix this by changing the intervention or excluding inconvenient random sets.

Amendment 2 requires at least a quarter (`PART87-DESIGN.md:115-117`).

   **Measured:** a full-size fixture with 1,560 registered question/sample/seed rows, only 98 genuinely generated observer-linked answers, and 1,462 deliberately wrong, ungenerated answer strings passes `replay87.main(... --fraction 0)`: **98 replayed, 0 mismatches, 0 problems**. The complete audit would reject the missing observer links; this is a primary-oracle contract bypass, not a claim that the combined runbook accepts that fixture. The runbook itself uses the correct default (`part87/RUNBOOK.md:89,98`). Reject fractions below 0.25, or label them as non-production overrides that cannot emit the normal PASS.

## Does replay implement the registered readings?

- **Reading 1: yes for the numerical recipe, subject to source identity above.** It renders one user turn with thinking off (`part87/replay87.py:134-136`), concatenates prompt and stored answer, tokenizes once without added special tokens (`:174-177`), and pools all positions in double-precision sums/counts (`:163-181`). The runner uses the same intended input (`part87/part87.py:329-339`), but sums each row in float32 before adding to a float64 accumulator (`:319-321`). The independent double sum is a useful difference, checked within the registered tolerance. All five residual medians use layer-output norms excluding position zero (`part87/replay87.py:139-154`), matching `part84/part84.py:43-55`.
- **Reading 2: yes for registered row seeds and ordinary calls.** Each replayed answer gets its own sampled call, CPU and device seed (`part87/replay87.py:239-255`); registered A seeds and B `phase:arm` keys are checked for every saved row (`:101-105,360-364`). The call's observed CPU seed must equal the row's seed (`:452-462`). Audit additionally checks the fresh CPU RNG state and recorded device initial seeds (`part87/audit87.py:372-379`). The quarter sample necessarily cannot certify arbitrary rare faults outside it, as replay itself documents (`part87/replay87.py:29-31`). That registered sampling limitation is distinct from finding 4.
- **Reading 3: the implemented independent intervention is right.** Python-float addition (`part87/replay87.py:197-219`), zeroing at every position (`:222-230`), own M/F arithmetic (`:189-198,286-300`), and stop-token construction (`:233-236`) match the amendment. Part 84's decode mode excludes the entire first prompt pass, including the pass producing the first answer token (`part84/part84.py:13-24,35-40`); replay's first-call flag does exactly that (`part87/replay87.py:208-218`). Enforcement still has finding 1's token/stop gap and cannot establish source-code arithmetic identity from identical output samples.
- **Questions, guards and indices: full-run rules match.** Replay uses Part 84's three origin questions, Part 66's direct/indirect lists, and guards at indices 25–30 (`part87/replay87.py:87-98,108-119`). Part 66 reserves 24 for the positive question and uses 25+ for guards (`part66/part66.py:73-85`). Main A/B/random row sets and all 49 arms total 1,560 (`part87/replay87.py:77-84,108-119`).
- **Pilot: only partly exact.** The design names 1 origin question x4 samples and 3 maker phrasings x2 (`PART87-DESIGN.md:69-71`), without selecting which phrasings. Replay appropriately avoids inventing their identities, but checks only totals 4/6 (`part87/replay87.py:110-115`), allowing J14's wrong grouping. It should validate group/sample structure while allowing any registered phrasings. Conversely audit hardcodes the first origin question and first three maker phrasings (`part87/audit87.py:110-117`), a narrower pilot choice than the design. The present runner uses that same permitted choice (`part87/part87.py:459-477`); this does not invalidate its intended pilot, but the audit should not describe that choice as the only registered one.

**Shared dependencies and possible common errors:** replay never imports `part87.py` (`part87/replay87.py:43-58,87-105,372-374`). It does share the tokenizer/chat-template implementation, transformers sampling/generate, and `neuron_report.load_model`; a defect in any of those can affect both sides identically (`neuron_report.py:154-166`). It also imports the actual Part 84/66 question/seed definitions and Part 25 matched-random implementation (`part87/replay87.py:87-105,374,415-416`). The imported random rule excludes targets and draws one per sorted target layer (`part25.py:735-747`), as registered. Sharing the registered parent rules is sensible, but changes to those files are not independently pinned by replay. Run/resume source hashes bind the run to its current sources (`part87/part87.py:82-99,417-419`); they do not establish those sources' intended correctness. The two concrete common-error paths measured here are accepting replacement source answers and equating decoded text with generated tokens. Same-device/library replay remains a required production check; CPU controls cannot establish XPU determinism.
