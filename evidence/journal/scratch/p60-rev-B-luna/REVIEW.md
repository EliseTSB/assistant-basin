## Findings

1. **High — 60j can recommend M0 when the tested candidate is M1.** `analyze60.py:380-406` allows M1 to become `test_candidate`; `analyze60.py:363-376` then compares that candidate’s gap to M1’s identical gap and requires a 5-point lead over it. If M1 wins dev and keeps a positive lead over M0 on test, the code still returns `improved = false` and recommends M0. The same prediction says “No method” even though only the dev-selected candidate is tested; `DEFINITIONS-60.md:39` correctly concedes that untested methods cannot be ruled out. **Scenario:** M1 is the best dev variant and beats M0 by 8 points on test; analysis says M0. **Smallest fix:** handle `best_dev == "M1"` by comparing M1 with M0, and describe 60j as the result for the tested candidate rather than all methods.

2. **Medium — M6 uses an unsupported thinking mode and can lose its answer to reasoning tokens.** `gen60.py:242-246` sets `thinking: {"type":"between_tools"}` for Haiku 5.5, while `gen60.py:35` caps M6 at 1,100 tokens. Anthropic’s current [thinking configuration docs](https://platform.claude.com/docs/en/build-with-claude/extended-thinking) describe adaptive thinking for Haiku 5.5; they also say thinking counts toward the hard `max_tokens` ceiling. A rejected batch makes M6 skipped or failed, so 60i cannot be scored. If changed to adaptive thinking without raising the ceiling/controlling effort, reasoning could consume much of the 1,100 tokens before the 12-sentence JSON is complete. **Smallest fix:** use Haiku 5.5’s supported adaptive configuration, set an effort and output ceiling that leaves room for the schema, and check truncation/stop reason in a live smoke request before the batch.

3. **Medium — the spend cap is not reserved before the API submission.** `gen60.py:445-451` checks `spend.jsonl`, but the first `reserve` event is appended only at `gen60.py:497-498`, after the POST returns. `RUNBOOK-60.md:9` says reservations are written before submission. **Scenario:** the process is killed after Anthropic accepts a batch but before the spend event is appended; another method’s submit then sees an undercount and can cross the $8 cap. The manifest stores a reserve amount but `spend_state()` does not read it. **Smallest fix:** durably append the reservation before POST, keyed by a local chunk ID; settle it on accepted batch and release it only on a definitive rejection.

4. **Medium — a batch-level rejection of M3/M5 second calls overwrites first-round evidence.** `gen60.py:472-484` replaces each eligible row with a generic skipped record for any 4xx. If M3 fresh or M5 round 2 is rejected, this discards the already collected selection/round-1 response, winner and usage data for those units. **Scenario:** M5 round 2 is rejected after round 1 was scored; the analysis can no longer report round-1 verified rate or full cost, and the manifest prevents retry. **Smallest fix:** preserve the existing row and attach a `fresh`/`round2` rejection status and usage under that phase.

5. **Low — the failure runner can leave a stale success archive.** `run60.sh:8-9,120-140` overwrites the ready archive only on success and never removes a prior one at start. On a supported rerun after a successful pass, a later failed phase leaves the earlier `part60-return.tgz` at the success path next to the incomplete archive. **Scenario:** an operator or file-based collector chooses the existing ready path after seeing a failed rerun and returns stale activations. **Smallest fix:** clear or uniquely version both return paths before starting each run, and write the run ID into the archive.

6. **Low — two regression checks do not exercise production behavior.** `test_part60.py:273-296` runs hard-coded toy calculations for own-text null leakage and M3 fresh scoring; those assertions still pass if `compute_thresholds()` starts including the target unit or `choose_m3_winners()` is changed. **Smallest fix:** construct small fixtures and call the production functions, asserting that the buggy implementation fails those tests.

7. **Low — the runbook omits the staging step its paths require.** `gen60.py:21-27` derives `BASIN` from its parent directory. In the reviewed location (`scratch/p60-build-B`), this resolves data under `scratch/results`; `RUNBOOK-60.md:17-20,47-62` instead invokes `part60/...` from `/home/elisepc/assistant-basin`. **Scenario:** running the reviewed build in place fails to find `pilot.jsonl` and Part 58 data. **Smallest fix:** document the copy/install of this build into `assistant-basin/part60` before the commands, or pass/configure the basin root explicitly.
