# Cold read: Part 165 reading job (prime/165-reading)

**Verdict.** Not ready to launch on the Arc tonight. As written, the job loads the 8 GB model, runs 16 forward passes, and then stops at `torch.stack` (reading165.py:423) because the frozen contexts are not 128 tokens: 15 of the 16 texts in `reading-texts.json` are 135–336 tokens, since the selection rule truncates when it tests and the file stores the untruncated text. Bar R4 cannot pass (`' Qwen'` is two tokens), so it would report a failure from missing data. Bar R5 is not the estimator the design registered, and the question-state inputs use the raw question rather than the chat prompt the effect run measured, at a different position. The direction builder is faithful to run165 (the host test passes and the code is identical in logic), decoder discovery is correct for both Qwen3.5 classes (checked on the real architecture with meta weights), and the A770 hazards you named are absent. The gates are weaker than the design says: G5 cannot detect a capture fault, G4 sits at the float32 noise floor, and a failed gate still writes its bars. Fix findings 1–4 before launch. Findings 5–16 do not stop the run but change what its numbers mean.

## Findings

1. **[critical] reading165.py:417–423, 308** — The 16 frozen texts do not tokenise to 128. Untruncated counts are 189,193,181,196,224,287,166,135,128,186,215,194,336,189,167,280. The selection at line 308 uses `truncation=True, max_length=SEQ`, so any text with ≥128 tokens passes and the full text is stored. `capture` then tokenises without truncation, and `torch.stack` at line 423 raises (verified: stack of [189,4] and [193,4] fails). The job dies after the model load. Fix: in `main`, tokenise each document with `truncation=True, max_length=SEQ` and assert every length is `SEQ` before the first forward. Then decide, and record in the design (PART165-READING-DESIGN.md:58–64), that the registered population is the first 128 tokens of each selected row, which is what the selection actually tested. Do not patch the file silently.

2. **[high] reading165.py:344–349, 498, 512–513, 595** — Bar R4 is unreachable. `' Qwen'` tokenises to `[1167, 16451]`, `' Tongyi'` to two tokens, `' Qwen3'` to three; only `' Alibaba'` (52540) is a single token. `frozen_readout` drops the rest, so `readout_qwen` is `None` for every row, the within-n+ key is skipped, `rho` is `None`, and `pass` is `False`. The output reads "R4 fail" with no measurement behind it. Fix needs a registered amendment (the design names `u_Qwen`): either name `' Alibaba'`, or define the Qwen covector on sub-token 1167 with a stated rule. In code, set `pass` to `None` when `rho` is `None`.

3. **[high] reading165.py:541–546 vs PART165-READING-DESIGN.md:113–116** — R5 is not the registered estimator. The code fits the slope on the n+ rows only, with no layer fixed effects, and transports it to the gap. The design specifies OLS of `log kl` on `log PR(w)` with layer fixed effects across all 6,912 rows, then the fraction of the n+−full gap that survives. Fix: fit `np.linalg.lstsq` on `[log_pr, one-hot layer]` over all records, and compute `explained = slope·(mean log_pr(n+) − mean log_pr(full)) / raw_gap`.

4. **[high] reading165.py:403, 420–426, 272–287** — The question states come from the wrong input and the wrong position. `question_ids` tokenises the raw question. The effect run used `common86.token_inputs` (common86.py:279–286), which applies `neuron_report.build_prompt` (neuron_report.py:363–370: chat template, `add_generation_prompt=True`, `enable_thinking=False`, `add_special_tokens=False`). The push also acts only on decode steps (`AddRowsHook`, common86.py:200–206 leaves the prefill untouched), and effect165 stores `scores[1]` and the hidden state from that step (effect165.py:116–121). So the measured KL is at the first generated token's position, not "the last prompt position" as the design says (PART165-READING-DESIGN.md:79–82). Fix: build the prompt with `build_prompt` (chat template, `add_special_tokens=False`), run one forward pass, take the argmax of the last-position logits as the first greedy token, append it, capture, and read the last position. The `proj`, `cos_state` and question-level `pc16` keys are affected. No bar uses them, but the design says they are the join.

5. **[medium] reading165.py:472–479 vs PART165-READING-DESIGN.md:127–130** — G5 is invariant to the capture site. Both the iso arm (`pinv @ g`, so `W·pinv·g = g` and the write is isotropic) and the null draws are isotropic directions in the same residual space. Their projection and cosine statistics have the same distribution whatever `X` is, so G5 passes by construction for any capture fault. The design's claim that it "validates the capture site" is false. Fix: add an explicit capture check (state shape `(SEQ, 2560)`, and `captured[L] == hidden_states[L+1][0]` for each layer below the last, as the host test does on the tiny model), and relabel G5 as a check of the direction construction only.

6. **[medium] reading165.py:190–192, 434–436** — G4 is at the float32 noise floor. The orthonormality check uses `atol=1e-6` on float32 eigenvectors. On synthetic `2048×2560` data through this same `pca()`, `max|PCᵀPC − I|` was 5.96e-7, 8.34e-7 and 1.07e-6 over three seeds, so the gate can trip on round-off and turn a clean run into FAIL. The non-negativity claim is also untested: `clamp_min(0)` at line 192 hides negative eigenvalues (synthetic float32 minimum −2.7e-4), so the gate does not check what the design says. Fix: compute the covariance in float64 on the CPU (`X.double()`, which is fine on the CPU and not on the XPU), check `eig ≥ −1e-8·max_eig` before clamping, and use a tolerance above the round-off floor.

7. **[medium] reading165.py:566–595, 597–598, 661 vs PART165-READING-DESIGN.md:131** — A failed gate does not stop the bars. The design says "a failed gate stops all readings". The code computes and writes every bar, with its `pass` value, into `reading.json`, and only the exit code (2) and the header line record the failure. Fix: when `gates["passed"]` is false, write the bars as `{"pass": None, "reason": "gate failed"}` and skip the within-arm and R-bar tables.

8. **[medium] reading165.py:508, 516–517 vs PART165-READING-DESIGN.md:108–110** — The bootstrap clusters on slot number alone, not on (layer, slot). `groups = [r["slot"] ...]` gives 12 clusters of 64 rows, not 96 clusters of 8. The reported `ci95` values are wrong. No bar uses the CI, so no bar flips. Fix: `groups = [(r["layer"], r["slot"]) ...]`, mapped to integers.

9. **[medium] reading165.py:292–313, 326–328, 405–411** — The gates do not check provenance or values. `natural_documents` silently falls back to the parquet if the texts file is missing (lines 292–296), against the design's "the job reads that file, not the parquet". `context_source` is written to the config but never gated. G3 checks only substring overlap and never token counts, and it never verifies `corpus_sha256` (which the texts file carries). G2 checks presence only, not `isfinite(kl)` or `isfinite(rel_change)`. Fix: fail if `context_source != "texts-file"`; assert the token counts (finding 1); compare the corpus SHA when the parquet is read; add `isfinite` to G2.

10. **[medium] reading165.py:341, 350** — The readout covector omits the `1 +` in the norm. `Qwen3_5RMSNorm.forward` multiplies by `(1.0 + self.weight)` (transformers 5.20 `modeling_qwen3_5.py:840`). The job uses `γ = weight`. The design's "positive scalar cancels" argument does not cover a per-coordinate `(1+γ)`. On the snapshot, `cos(γ⊙u, (1+γ)⊙u)` for `' Alibaba'` is 0.998, a small but real error. Fix: `gamma = 1.0 + parent.norm.weight.detach().float()`.

11. **[medium] reading165.py:109–136 vs neuron_report.py:154–166 and run165.py:164** — The loader is not the house loader, although its docstring says it is. It uses `torch_dtype=`, `device_map={"": device}` and a monkeypatch of `caching_allocator_warmup`. The house loader, which produced the effect run on the Arc, uses `dtype=torch.bfloat16`, no `device_map`, and `model.to(device)`. The `device_map` path to XPU has not been run on the A770. The reading's path does avoid a 7.5 GB CPU copy, which helps the RAM guard, but that is unverified on Windows. Fix: copy the house call exactly (`dtype=`, the same fallback), or run the `device_map` path once on the Arc before the real run.

12. **[medium] test_reading165.py:38, 145–146, 183–192** — The tests do not cover the contract. The tiny model is `Qwen3ForCausalLM`, not Qwen3.5, so the image-text decoder path is untested by the suite (the meta-device check in the paragraph after the findings covers its decoder discovery). The fixture texts are both 401 tokens, so the stack passes by coincidence and finding 1 is hidden. Only G1 has a failure test; G2, G3, G4 and G5 have none. Fix: add a test with a real 128-token fixture and a document of another length (expect a clear error), plus one failure test per gate.

13. **[low] reading165.py:444** — The null rows omit `mean_abs_cos_vocab` (passed `None`), but the design (PART165-READING-DESIGN.md:99–101) says the null carries measures 1–3, and measure 3 includes the vocabulary mean. Fix: sample the 2,000 vocabulary rows for the null too.

14. **[low] reading165.py:176** — `capture` reads `output[0]`, which is correct only where decoder layers return a bare tensor. transformers 5.20 `Qwen3_5DecoderLayer` returns a tensor, and the repo records 5.20.0 widely, so this is probably fine. If the Arc returns a tuple, states become `[1,128,2560]`, `state_dim` becomes 128 (line 422), and the null geometry fails at line 444. effect165.py:26–27 handles both forms; the same handling belongs here: `output[0] if isinstance(output, (tuple, list)) else output`.

15. **[low] reading165.py:491–498, 512–513 vs PART165-READING-DESIGN.md:146** — The R4 bound is stated as "a bound with 768 rows", but `readout_qwen` and the other per-slot measures are constant over the eight questions of each slot, so the effective sample is 96 slots. The bar's decision uses the same point estimate, so this overstates the precision of the bound rather than changing the verdict. Fix: state 96 effective units in the design, or report the slot-clustered CI beside the point estimate.

16. **[low] part165/steps-reading.txt:6; tools/part_check.py** — The launch line uses the placeholder `NN`, which `launch_arc.py` rejects (it requires `\d+[a-z]?`). Separately, the prelaunch check validates `PART165-DESIGN.md` (dry run: 20 checks passed) and not the reading design this job runs under. Fix: substitute `165` in the steps file, and have the check name or verify the design the steps file cites.

**Checked and found correct:** the direction builder matches run165's `_seeded_raw` and `build_directions` (same draws, order and scaling; the host test passes 6/6). `find_text_decoder` finds the 32-layer `ModuleList` under `Qwen3_5TextModel`, which has `norm` and `embed_tokens`, for both `AutoModelForCausalLM` and `AutoModelForImageTextToText` on the snapshot config (meta device). The frozen question list equals `part164.choose_questions()[:8]` and is all maker. The corpus SHA is `74da360f…`, and the job's selection rule reproduces the frozen row indices and texts. There is no float64 on the XPU, no `topk`, and no per-value `.item()` in a hook. Every file open specifies `encoding='utf-8'`. Relative paths resolve, because `job.py` sets `cwd` to the job folder and `--copy` keeps relative paths.
